# แผนการทำ Feature Engineering ตามกรอบสมมติฐานวิจัย (`data/integrated/country_year.csv`)

เอกสารนี้ออกแบบกระบวนการทำ Feature Engineering ให้ตรงกับสมมติฐานวิจัยทั้ง 3 ข้อของคุณ (**$H_1$ ความเปิดรับดิจิทัล, $H_2$ เศรษฐกิจ, และ $H_3$ ความพร้อมด้านไซเบอร์ต่อการเป็นต้นทางโจมตี**) โดยปรับปรุงตัวเลขสถิติจริงทุกตัวและผนวกแนวทางป้องกันปัญหาทางระเบียบวิธีวิจัยจาก `pre_fea.md` (เฉพาะส่วนที่ทดสอบแล้วว่าส่งผลดีต่อโมเดลและการพิสูจน์สมมติฐานจริง)

---

## 1. การคัดกรองแถวก่อนเริ่มทำฟีเจอร์ (Row Filtering — สำคัญมาก)

ในไฟล์ `data/integrated/country_year.csv` มีทั้งหมด **753 แถว** (251 พื้นที่ × 3 ปี: 2022–2024) ก่อนคำนวณฟีเจอร์ต้องคัดกรองแถวด้วย 2 คอลัมน์ที่มีอยู่ในตารางแล้ว ดังนี้:

| เงื่อนไขการกรองแถว | ต้องทำอะไร | เพราะอะไร (เหตุผลจากข้อมูลจริง) |
| :--- | :--- | :--- |
| **`in_worldbank == True`** | เก็บเฉพาะแถวที่เป็น `True` (ตัดออก 102 แถว เหลือ 651 แถว / 217 ประเทศ) | พื้นที่ที่เป็น `False` คือเกาะหรือดินแดนพิเศษ 34 แห่ง (เช่น แอนตาร์กติกา `ATA`, เกาะโบแนร์ `BES`) ซึ่ง**ไม่มีข้อมูลเศรษฐกิจ (`gdp_per_capita`, `fdi_net_inflows`) และไม่มีข้อมูลอินเทอร์เน็ต (`internet_users_pct`, `broadband_subs_per_100`) เลย 100%** |
| **`traffic_above_0_01pct == True`** | เก็บเฉพาะแถวที่มี `http_traffic_mean >= 0.01%` (ได้กลุ่มประเทศวิเคราะห์หลัก **432 แถว / 144 ประเทศ**) | เพราะตัวแปรตาม $Y$ ของเรานำทราฟฟิกมาเป็น**ตัวหาร** ประเทศหรือเกาะเล็กๆ ที่มีทราฟฟิกใกล้ `0` (เช่น `0.00001%`) เมื่อนำไปหาร `% การโจมตี` จะทำให้ผลหารพุ่งทะลุหลักพันโดยไม่ได้เกิดจากการโจมตีจริง แต่เกิดจากตัวหารใกล้ศูนย์ (Small-Denominator Outlier) |

## 2. ตัวแปรตาม ($Y$): ความเข้มข้นของการโจมตีเทียบกับขนาดทราฟฟิก

งานวิจัยของคุณแบ่งตัวแปรตาม ($Y$) ออกเป็น **2 ฝั่ง** ตามสมมติฐาน คือ **ฝั่งผู้ถูกโจมตี (Target — สำหรับ $H_1, H_2$)** และ **ฝั่งต้นทางการโจมตี/บอทเน็ต (Origin — สำหรับ $H_3$)** โดยใช้หลักการหารด้วยขนาดทราฟฟิกแล้วใส่ `log` เหมือนกัน:

### 2.1 ตัวแปรตามสำหรับ $H_1$ และ $H_2$ (ฝั่งเป้าหมายที่ถูกโจมตี): `attack_intensity_log`
$$\text{attack\_intensity\_log} = \ln\left(\frac{\text{target\_ddos\_percent} + 10^{-4}}{\text{http\_traffic\_mean} + 10^{-4}}\right)$$

* **ปัญหาที่พบในข้อมูลจริง (กลุ่มหลัก 432 แถว):**
  * มีแถวที่ `target_ddos_percent` เป็นค่าว่าง (`NaN`) อยู่ **29 แถว** และเป็นค่า `0.0` อยู่แล้วอีก **4 แถว** $\rightarrow$ รวมแถวที่เป็นศูนย์หลังเติมค่าทั้งหมด **33 แถว (จาก 17 ประเทศ; ปีละ 11 แถวเท่ากันในปี 2022, 2023, 2024)**
* **ต้องทำอะไร & เพราะอะไร:**
  1. **เติมค่าว่าง `NaN -> 0.0` และสร้างคอลัมน์ Flag `is_target_ddos_censored = (target_ddos_percent.isna() | (target_ddos_percent == 0)).astype(int)`:**
     * ใน Cloudflare API การดึงอันดับประเทศที่ถูกโจมตี DDoS จะคืนค่าเฉพาะประเทศที่ติดอันดับ Top Limit ประเทศที่มีทราฟฟิกปกติ (`>= 0.01%`) แต่ค่าว่างหรือเป็น `0` คือประเทศที่ถูกโจมตีต่ำกว่าขีดจำกัดการรายงานของ API (Left-censored near zero)
  2. **บวกค่าคงที่ $\varepsilon = 10^{-4}$ (`0.0001%`) ทั้งเศษและส่วนก่อนใส่ `np.log`:**
     * ป้องกัน $\ln(0) = -\infty$ (`-inf`) และลดความเบ้ (Skewness) จากค่าดิบ **`+8.05` ลงมาเหลือ `-0.39`** (โดยถ้าคิดเฉพาะ 399 แถวที่ไม่เป็นศูนย์ ความเบ้จะเท่ากับ **`-0.22`**)
     * **ข้อควรระวัง (จากผลทดสอบโมเดลจริง):** ไม่ควรใช้วิธีเติมด้วยค่าครึ่งหนึ่งของค่าต่ำสุดในตารางรวม (`half-min = 5e-7`) เพราะจะดึงค่า $Y$ ของ 33 แถวลงไปถึง `-15.28` ทำให้ความเบ้แย่ลงเป็น `-1.29` และทำให้ค่า RMSE ของโมเดลบนชุด Test แย่ลงถึง `+45%` (จาก `1.951` เป็น `2.836`)
  3. **การทำ Sensitivity Check สำหรับ 33 แถวที่เป็นศูนย์:**
     * เนื่องจากค่า $Y$ ของ 33 แถวนี้ถูกกำหนดโดยค่า $\varepsilon$ (อยู่ในช่วง `-9.99` ถึง `-4.69`) ในขั้นพิสูจน์สมมติฐาน $H_1, H_2$ และขั้นเทรนโมเดล **ให้รันเปรียบเทียบ 2 ชุดควบคู่กันเสมอ** คือ:
       * **ชุดหลัก (Full Core = 432 แถว):** เติม `0` + $\varepsilon = 10^{-4}$ (ให้ค่า Test 2024 $R^2$ สูงสุด: Ridge `+0.274`, Random Forest `+0.497`)
       * **ชุดตรวจสอบความไว (Uncensored Core = 399 แถว, กรอง `is_target_ddos_censored == 0`):** ตัด 33 แถวที่ไม่ติดเพดาน API ออก เพื่อยืนยันว่าผลสมมติฐานไม่ได้เกิดจากค่า $\varepsilon$ (ชุดนี้ให้ค่า GroupKFold $R^2$ ดีขึ้นจาก `+0.146` เป็น `+0.168` และ RMSE ต่ำลงเหลือ `1.804`)

### 2.2 ตัวแปรตามสำหรับ $H_3$ (ฝั่งต้นทางบอทเน็ต/การโจมตี): `origin_ddos_intensity_log` (และตัวเปรียบเทียบ `origin_l7_intensity_log`)
กำหนดชื่อคอลัมน์ในโค้ดให้เป็นมาตรฐานเดียวกัน (ใส่ $\varepsilon = 10^{-4}$ เหมือนฝั่ง Target ทุกประการ):
1. **ตัวแปรตามหลักของ $H_3$ (`origin_ddos_intensity_log`):**
   $$\text{origin\_ddos\_intensity\_log} = \ln\left(\frac{\text{origin\_ddos\_percent} + 10^{-4}}{\text{http\_traffic\_mean} + 10^{-4}}\right)$$
2. **ตัวแปรตามทางเลือกของ $H_3$ (`origin_l7_intensity_log`):**
   $$\text{origin\_l7\_intensity\_log} = \ln\left(\frac{\text{origin\_l7\_mitigated\_percent} + 10^{-4}}{\text{http\_traffic\_mean} + 10^{-4}}\right)$$

* **สถานะข้อมูลจริง (กลุ่มหลัก 432 แถว) — สมบูรณ์ 100%:**
  * ทั้ง `origin_ddos_percent` และ `origin_l7_mitigated_percent` **ไม่มีค่าว่างเลย (`0 แถว`) และไม่มีค่าศูนย์เลย (`0 แถว`)** ในกลุ่ม 144 ประเทศหลัก (จึงไม่มีปัญหาเรื่องค่า $\varepsilon$ เหมือนฝั่ง Target)
  * **ผลลัพธ์หลังแปลง:**
    * `origin_ddos_intensity_log`: ความเบ้ลดจากค่าดิบ **`+7.00` เหลือ `-0.03`** (สมมาตรเกือบ 100%)
    * `origin_l7_intensity_log`: ความเบ้ลดจากค่าดิบ **`+6.97` เหลือ `+0.21`**
  * **การตีความ:** ค่า **`> 0`** แปลว่าประเทศนั้นเป็นต้นทางปล่อยทราฟฟิกโจมตี/บอทเน็ต**มากกว่า**สัดส่วนทราฟฟิกอินเทอร์เน็ตปกติของตัวเอง และค่า **`< 0`** แปลว่าเป็นต้นทางโจมตี**น้อยกว่า**ขนาดทราฟฟิกของตัวเอง

> [!NOTE]
> **ข้อจำกัดและการตรวจสอบความไวของตัวหาร `http_traffic_mean` (Causal Traffic Denominator Check):**
> เนื่องจากปี 2022 ไม่มีคอลัมน์ `http_traffic_percent` รายปี คอลัมน์ `http_traffic_mean` จึงเป็นค่าเฉลี่ยของปี 2023–2024 (ทำให้แถวปี 2022–2023 ในชุด Train มีค่าทราฟฟิกปี 2024 ผสมอยู่ในตัวหารเล็กน้อย) อย่างไรก็ตาม จากการทดสอบสร้างตัวหารแบบไร้ข้อมูลปี 2024 (`http_traffic_causal_pct`: ให้ปี 2022–2023 ใช้ค่าทราฟฟิกของปี 2023 ล้วนๆ และปี 2024 ใช้ของปี 2024) พบว่ามีสหสัมพันธ์กับตัวเดิมสูงถึง **`r = 0.9923`** และให้ผลโมเดล Test $R^2$ ต่างกันเพียง `0.001` (`+0.273` vs `+0.274`) จึงสามารถสร้าง `attack_intensity_causal_log` เก็บไว้เป็นตัวแปรยืนยันความถูกต้อง (Sensitivity Check) ได้อีกหนึ่งคอลัมน์

## 3. คอลัมน์ฐาน (Control / Baseline Features) และรายการคอลัมน์ต้องห้าม (Exclusion List)

### 3.1 คอลัมน์ฐาน 3 ตัว (ใช้คุมผลในทุกสมมติฐาน $H_1, H_2, H_3$)

| คอลัมน์ต้นฉบับ | ชื่อฟีเจอร์ในโค้ด | สถานะในกลุ่มหลัก (432 แถว) | ต้องทำอะไร (What to do) | เพราะอะไร (Why) |
| :--- | :--- | :--- | :--- | :--- |
| `http_traffic_mean` | **`http_traffic_mean_log`** | **ว่าง 0 แถว (ครบ 100%)**<br>ช่วงค่า: `0.011% – 24.51%`<br>ความเบ้ดิบ: **`+11.42`** | เทค `np.log(http_traffic_mean)` แล้วทำ `StandardScaler` | • ลดความเบ้จาก **`+11.42` เหลือ `+0.46`**<br>• **ข้อควรระวังในการอ่านค่าสัมประสิทธิ์ ($\beta$):** เนื่องจาก $Y = \ln(\text{attack}) - \ln(\text{traffic})$ ค่าสัมประสิทธิ์ $\beta_{\text{traffic}}$ ในสมการที่มียังมี $\ln(\text{traffic})$ เป็นตัวแปรต้น จะมีความหมายเท่ากับ **(ความยืดหยุ่นของการโจมตีต่อทราฟฟิก $- 1$)** คือถ้า $\beta_{\text{traffic}} > 0$ แปลว่าประเทศทราฟฟิกใหญ่โดนโจมตีเพิ่มขึ้นในอัตราที่เร็วกว่าขนาดทราฟฟิก |
| `population` | **`population_log`** | **ว่าง 0 แถว (ครบ 100%)**<br>ช่วงค่า: `1.2 แสน – 1.45 พันล้านคน`<br>ความเบ้ดิบ: **`+8.75`** | เทค `np.log(population)` แล้วทำ `StandardScaler` | ขนาดประชากรต่างกันระดับหมื่นเท่า หลังใส่ `log` ความเบ้ลดจาก **`+8.75` เหลือ `-0.07`** ช่วยคุมอิทธิพลขนาดประชากรได้อย่างแม่นยำ |
| `year` | **`year`** (และ `year_idx`) | **ว่าง 0 แถว (ครบ 100%)**<br>ค่า: `2022, 2023, 2024` | • **ตอนพิสูจน์สมมติฐาน (Regression):** แปลงเป็น `year_idx = year - 2022` (`0, 1, 2`) หรือ Dummy (`year_2023`, `year_2024`)<br>• **ตอนเทรนโมเดลทำนาย:** ใช้ `year` เป็นตัวแบ่ง **Train (`2022–2023`) / Test (`2024`)** | ช่วยคุมผลความผันผวนของการโจมตีระดับโลกที่เปลี่ยนไปในแต่ละปี และใช้แบ่ง Train/Test ตามเวลาจริง |

### 3.2 รายการคอลัมน์ต้องห้ามใส่เป็นตัวแปรต้น $X$ เด็ดขาด (Target Leakage Exclusion List)
ในการเขียนโค้ดเลือก Features ($X$) เข้าโมเดล **ห้ามดึงคอลัมน์ต่อไปนี้เข้าในเมทริกซ์ $X$ เด็ดขาด** เพราะเป็นองค์ประกอบโดยตรงหรือตัวแทนของคำตอบ $Y$:
* กลุ่มตัวตั้งของ $Y$: `target_ddos_percent`, `origin_ddos_percent`, `target_l7_mitigated_percent`, `origin_l7_mitigated_percent` (รวมถึงตัวแปรตาม $Y$ อีกฝั่ง เช่น ห้ามเอา `origin_ddos_intensity_log` ไปทำนาย `attack_intensity_log`)
* กลุ่มตัวหารและองค์ประกอบการโจมตีในปีเดียวกัน: `http_traffic_percent`, `http_traffic_mean` (ใช้เฉพาะตัวที่เทค `log` เป็นคอลัมน์ฐานแล้ว), `origin_mitig_waf_percent`, `origin_mitig_ddos_percent`, `origin_mitig_bot_percent`, `l3_top_vector`, `l3_syn_percent`, `l3_udp_percent`, และ `is_target_ddos_censored`

## 4. รายละเอียดการทำ Feature Engineering แยกตามสมมติฐาน ($H_1, H_2, H_3$)

### 4.1 สมมติฐาน $H_1$: ความเปิดรับดิจิทัล (Digital Exposure)
* **สมมติฐาน:** ประเทศที่คนใช้เน็ตมากและมีโครงข่ายใหญ่ โดนโจมตีมากกว่าส่วนแบ่ง traffic ของตัวเอง (คาดหมายทิศทางสัมประสิทธิ์: **เป็นบวก $\beta > 0$**)
* **ตัวแปรตาม ($Y$):** `attack_intensity_log`
* **ตัวแปรต้น ($X$):** คอลัมน์ฐาน + `internet_users_pct` + `broadband_subs_per_100` + `routed_asn_count_log` *(ตัวหลัก)* หรือสลับเทียบกับ `ipv4_slash24_count_log` *(ตัวรอง)*

| ฟีเจอร์ใน $H_1$ | ปัญหาในข้อมูลจริง (กลุ่มหลัก 432 แถว) | ต้องทำอะไร (What to do) | เพราะอะไร (Why) |
| :--- | :--- | :--- | :--- |
| **`internet_users_pct`**<br>(% ประชากรที่ใช้เน็ต) | • **ว่าง 25 แถว (`5.8%`)** ส่วนใหญ่วางในปี 2023–2024<br>• ช่วงค่า: `8.95% – 100%`<br>• ความเบ้ก่อน `ffill` `-0.98` / หลัง `ffill` **`-1.23`** | 1. **เติมค่าว่างด้วย Forward-Fill (`ffill`) รายประเทศ** จากไฟล์ `data/cleaned/wb_digital.csv` (ปี 2018–2023) $\rightarrow$ **ค่าว่างลดจาก 25 แถว เหลือเพียง 6 แถว** (คือ ซูดาน `SDN` และเติร์กเมนิสถาน `TKM`)<br>2. อีก 6 แถวที่เหลือเติมด้วยค่ามัธยฐาน (Median) ของชุด Train<br>3. **ไม่ต้องใส่ `log`** แต่ให้ทำ `StandardScaler` | • สัดส่วนผู้ใช้เน็ตของประเทศเดียวกันเปลี่ยนช้ามากในระยะ 1–2 ปี การดึงค่าปีก่อนหน้าของประเทศตัวเอง (`ffill`) แม่นยำและไม่รั่วไหลจากอนาคต<br>• ข้อมูลมีขอบเขต `0–100%` และเบ้ซ้าย (`-1.23`) หากใส่ `log` จะยิ่งเบ้ซ้ายหนักขึ้น |

## 5. แนวทางทางสถิติสำหรับการพิสูจน์สมมติฐานและการประเมินโมเดล (แก้ปัญหาโครงสร้างข้อมูล Panel 3 ปี)

จากการตรวจสอบโครงสร้างความแปรปรวนของข้อมูล 432 แถว (144 ประเทศ × 3 ปี) พบลักษณะสำคัญของข้อมูลที่ต้องกำหนดวิธีรันสถิติและประเมินโมเดลไว้ล่วงหน้า ดังนี้:

1. **ความแปรปรวนของตัวแปรต้น ($X$) เกิดจากความต่างระหว่างประเทศ (Between-Country) ถึง ~99%:**
   * สัดส่วนความแปรปรวนภายในประเทศเดียวกันข้ามปี (Within-country variance share) ของ `http_traffic_mean_log` = `0.000`, `routed_asn_count_log` = `0.002`, `gdp_per_capita_log` = `0.003`, `gov_effectiveness` = `0.004`, `internet_users_pct` = `0.009`, และ `gci_score_100` = `0.083` (ขณะที่ตัวแปรตาม $Y$ มีความแปรปรวนข้ามปี `0.161 – 0.258`)
   * **สิ่งที่ต้องทำตอนพิสูจน์สมมติฐาน ($H_1, H_2, H_3$):**
     * ห้ามใช้ Standard Error ของ OLS แบบปกติ (เพราะการนับประเทศเดิมซ้ำ 3 ปีจะทำให้ค่า Standard Error เล็กเกินจริงประมาณ $\sqrt{3}$ เท่า และได้ $p$-value ต่ำเกินจริง)
     * **ต้องใช้ Cluster-Robust Standard Errors จัดกลุ่มตามรหัสประเทศ (`cov_type='cluster', cov_kwds={'groups': df['iso3']}` สำหรับ 144 คลัสเตอร์)** ในทุกสมการ Regression
     * กำหนดทิศทางการทดสอบตามสมมติฐาน ($H_1, H_2$: $\beta > 0$, $H_3$: $\beta < 0$ ที่ระดับนัยสำคัญ $\alpha = 0.05$) พร้อมรายงานค่า $p$-value ที่ปรับแก้การทดสอบหลายสมมติฐานด้วยวิธี **Holm-Bonferroni (หรือ Benjamini-Hochberg FDR)**
   * **เกณฑ์การตรวจสอบ Multicollinearity (VIF):**
     * กำหนดเกณฑ์ว่า **ตัวแปรสมมติฐานหลักที่ต้องการแปลผลต้องมีค่า $\text{VIF} < 5.0$** (ซึ่งในแผนนี้ผ่านเกณฑ์ทุกตัว: $H_1$ ใช้ `routed_asn_count_log` ได้ $\text{VIF} = 4.57$, $H_2$ ได้ $\text{VIF} \le 5.24$, $H_3$ ได้ $\text{VIF} \le 3.91$; ส่วนคอลัมน์ฐาน `http_traffic_mean_log` และ `population_log` ที่ใส่ไว้เป็นตัวควบคุมขนาดอนุญาตให้มี VIF สูงได้ตามหลักเศรษฐมิติเพราะไม่ได้ใช้แปลผลเป็นสมมติฐานหลัก และในขั้น ML จะใช้ Ridge / Tree-based models ที่ทนต่อ Collinearity)

2. **การประเมินโมเดล Machine Learning ควบคู่กัน 2 มิติ (Temporal Split + Country GroupKFold):**
   * เนื่องจากประเทศเดียวกันปรากฏอยู่ทั้งในชุด Train (ปี 2022–2023) และชุด Test (ปี 2024) โมเดลอย่าง Random Forest สามารถทำนายปี 2024 ได้แม่นยำขึ้น ($R^2 \approx 0.50$) ส่วนหนึ่งจากการจดจำระดับพื้นฐานของแต่ละประเทศ
   * ดังนั้น ในขั้นตอนการประเมินโมเดล (Step 9 ใน `docs/architecture.md`) **ให้รายงานผลคู่กันทั้ง 2 รูปแบบ**:
     1. **Temporal Split (Train 2022–2023 $\rightarrow$ Test 2024):** วัดความแม่นยำในการพยากรณ์อนาคตของประเทศเดิมในปีถัดไป
     2. **5-Fold `GroupKFold(groups=df['iso3'])`:** วัดความสามารถของโมเดลในการทำนาย **"ประเทศใหม่ที่ไม่เคยเห็นในชุด Train เลย"**

## 7. ลำดับขั้นตอนการประมวลผลในโค้ด (Pipeline Execution Order)

1. **ขั้นที่ 1 (Causal Forward-Fill):** นำตารางปี 2018–2024 จาก `data/cleaned/wb_econ.csv` และ `data/cleaned/wb_digital.csv` มาทำ `groupby('iso3').ffill()` (ดึงเฉพาะอดีตมาเติมปัจจุบัน) แล้วเชื่อมเข้ากับตารางปี 2022–2024
2. **ขั้นที่ 2 (Row Filtering):** กรองเฉพาะ `in_worldbank == True` และ `traffic_above_0_01pct == True` (ได้ **432 แถว / 144 ประเทศ**)
3. **ขั้นที่ 3 (Target & Log Transforms + Flags):** สร้างคอลัมน์ Flag (`is_target_ddos_censored`, `has_gci`, `has_vdem`), คำนวณตัวแปรตาม $Y$ (`attack_intensity_log`, `origin_ddos_intensity_log`, `origin_l7_intensity_log`), คำนวณ `gci_z_within_edition` แยกตามฉบับ GCI, และเทค `np.log` กับตัวแปรเบ้ขวา
4. **ขั้นที่ 4 (Temporal Train/Test Split):** แบ่งข้อมูลตามปี — **Train = ปี 2022–2023 (288 แถว)** และ **Test = ปี 2024 (144 แถว)** (พร้อมเตรียม `GroupKFold(n_splits=5)` ตาม `iso3`)
5. **ขั้นที่ 5 (Fit Median Imputer, Clipping Bounds & StandardScaler บน Train เท่านั้น):** คำนวณค่า Median สำหรับแถวที่ยังว่าง (`SDN, TKM, XKX, PRI, SYR, HKG, MAC, BHS, BRN`), ขอบเขต Clipping `[p2.5, p97.5]` ของ FDI (`[-6.62, +15.54]`), และค่า Mean/SD ของ `StandardScaler` **จากชุด Train เท่านั้น** แล้วนำไปแปลงทั้งชุด Train และ Test ก่อนบันทึกลง **`data/analytical/features.csv`** และตาราง **`features` ในฐานข้อมูล SQLite (`data/warehouse/cyberattacks.db`)**
